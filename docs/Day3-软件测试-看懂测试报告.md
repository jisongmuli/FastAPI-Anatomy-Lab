## 1. 三分钟建立测试的世界观

### 测试到底在回答什么问题？

不是"代码写得好不好"，而是：**"我改了这里，会不会把那里弄坏？"**

软件测试的本质是**用可重复的方式，把'我以为它对'变成'我能证明它对'**。

### 测试金字塔（这是组会最常被提到的图）

```
        ▲  少
       ╱ ╲      端到端测试 (E2E)      真浏览器点按钮，最像真实用户，最慢最脆
      ╱───╲
     ╱     ╲    集成测试 (API 测试)   TestClient 走完整 HTTP 链路  ← 本项目 test_tasks_api.py
    ╱───────╲
   ╱         ╲  单元测试 (Unit)       只测一个函数，最快最准        ← 本项目 test_tasks_service.py
  ╱───────────╲
        ▼  多
```

| 类型 | 在本项目里是哪个文件 | 怎么调用 | 运行速度 | 坏了说明什么 |
|---|---|---|---|---|
| 单元测试 | `tests/test_tasks_service.py` | 直接 `service.create_task(db, payload)` | 极快 | **某条业务规则写错了** |
| 集成/接口测试 | `tests/test_tasks_api.py` | `client.post("/api/v1/tasks", json=...)` | 快 | **接口层接错了**（路由/校验/状态码） |
| 冒烟测试 | `tests/test_health.py` | `client.get("/health")` | 极快 | **服务根本起不来** |

**测试金字塔的原则：下面越多越好，上面越少越好。**
本项目 29 个用例里，大部分是单元和接口测试，没有 E2E —— 这是合理的，不是偷懒。

## 2. pytest 的最小知识（只要 5 个概念）

### 概念 1：测试文件与被测函数怎么对应

| 被测代码 | 对应测试文件 | 命名规则 |
|---|---|---|
| `app/service.py` | `tests/test_tasks_service.py` | 文件名 `test_*.py` 或 `*_test.py` |
| `app/routes/tasks.py` | `tests/test_tasks_api.py` | 函数名必须以 `test_` 开头 |
| `app/main.py` 的 /health | `tests/test_health.py` | 类名（如果用类）必须 `Test` 开头 |

> **只有名字符合规则的才会被自动收集。** 本项目里那个 `演示-失败的测试.py` 故意不叫 `test_`，
> 所以默认 `pytest` 不会跑它，必须手动指定文件。你可以用这个规则来"隔离"不想每次跑的用例。

### 概念 2：一个用例固定三段式（Arrange-Act-Assert）

```python
@pytest.mark.integration
def test_create_then_read_task(client: TestClient) -> None:
    # ---- Arrange 准备：造数据、准备请求 ----
    payload = {"title": "读论文 5 篇", "priority": 4}

    # ---- Act 执行：真的发一次请求 ----
    create_resp = client.post(TASKS_URL, json=payload)

    # ---- Assert 断言：先状态码，再内容 ----
    assert create_resp.status_code == 201
    assert create_resp.json()["title"] == "读论文 5 篇"
```

**读测试用例时，找到这两样就够看懂它：`client.get/post/...`（做了什么）和 `assert`（期望什么）。**

> 好的断言顺序：**先断状态码，再断字段**。因为状态码不对时，后面的字段断言全是噪音。

### 概念 3：fixture（夹具）= 用例的"统一开局"

`tests/conftest.py` 定义了三个夹具：

| 夹具名 | 提供什么 | 用完怎么清 |
|---|---|---|
| `db_session` | 一个干净的数据库会话 | 关连接 + 删表 |
| `client` | 能发假 HTTP 请求的 TestClient | 清除依赖覆盖 |
| `sample_task` | 一条已创建好的任务 | — |

用法就是**把夹具名写成参数**：
```python
def test_xxx(client: TestClient, sample_task: dict):   # ← 要什么写什么，pytest 自动注入
```

**为什么必须用夹具？** 因为要保证**用例之间互不干扰**：
每个用例都从"空数据库"开始，这样第 3 个用例失败时，你能确定是它自己的问题，而不是被第 1 个用例污染了。

本项目专门写了一个用例守着这条规则：
```python
def test_each_test_starts_with_empty_database(client):
    assert client.get(TASKS_URL).json()["total"] == 0
```
**它能通过 = 隔离性没坏。** 哪天它开始失败，说明测试代码自己出 bug 了。

### 概念 4：`pytest.raises` = 断言"这里应该报错"

```python
def test_get_task_raises_when_missing(db_session):
    with pytest.raises(TaskNotFound) as exc_info:      # 期望抛出这个异常
        service.get_task(db_session, 999)

    assert exc_info.value.task_id == 999               # 顺便检查异常里带的信息
```
**只测正常路径是不够的**，真正容易出 bug 的是异常路径。

### 概念 5：`parametrize` = 一份逻辑跑多组数据

```python
@pytest.mark.parametrize("bad_payload, reason", [
    ({}, "缺少必填的 title"),
    ({"title": ""}, "title 不允许空字符串"),
    ({"title": "x" * 101}, "title 超过 100 字上限"),
    ({"title": "正常", "priority": 0}, "priority 小于下限 1"),
    ({"title": "正常", "priority": 6}, "priority 超过上限 5"),
    ({"title": "正常", "status": "finished"}, "status 只能是 pending/doing/done"),
])
def test_invalid_payload_returns_422(client, bad_payload, reason):
    assert client.post(TASKS_URL, json=bad_payload).status_code == 422
```
报告里会显示成 6 个独立用例，**哪组数据坏了看得清清楚楚**。这是做"边界值测试"最实用的工具。

**这份报告告诉你 6 件事，逐项读法：**

| 输出 | 含义 | 你要关注的 |
|---|---|---|
| `rootdir` + `configfile` | 在哪个目录、用的哪个配置 | 如果目录不对，说明你在错的地方执行了命令 |
| `plugins` | 装了哪些插件 | 有 `cov` 才能用 `--cov` |
| `collected 29 items` | 一共收集到 29 个用例 | **数字突变要警惕**（比如昨天 29、今天 12） |
| `....` / `F` / `s` / `E` | 每个点＝通过，F＝失败，s＝跳过，E＝出错 | 一眼看密度就知道哪里聚集了失败 |
| `29 passed` | 全过 | 这是"绿灯"，可以继续 |
| `0.26s` | 耗时 | 单元/接口测试应该是**亚秒级**；几秒以上说明设计有问题 |

### ❌ 有失败时（真实的红色输出，本项目实测）

```
_______________ test_故意不存在的接口 ________________
tests\演示-失败的测试.py:56: in test_故意不存在的接口
    assert client.get("/api/v1/not-exist").status_code == 200

E    +  where 404 = <Response [404 Not Found]>.status_code

FAILED tests/演示-失败的测试.py::test_故意不存在的接口 - AssertionError: asse...
=================== 3 failed, 1 passed, 1 warning in 0.19s ====================
```

**读失败信息的三步法**（这是今天最值钱的技能）：

| 步骤 | 看哪里 | 得到什么 |
|---|---|---|
| ① 看失败**位置** | `tests\演示-失败的测试.py:56` | 哪个文件第几行（点击可跳转） |
| ② 看**断言对比** | `assert 404 == 200` | **左边是实际值，右边是你期望的值** |
| ③ 看**上下文** | 下面的 `where ... = get('/api/v1/not-exist')` | 是哪个请求、哪个对象产生的 |

然后问自己一个问题，答案决定下一步：
> **"是代码错了，还是我的测试写错了？"**

- 如果 `期望 201、实际 200` → 可能是你的断言写错了，也可能是代码没按设计返回
- 如果 `期望 200、实际 404` → 地址拼错 / 路由没挂上 / 数据没创建成功
- 如果 `期望 204、实际 500` → 服务端真的出 bug 了，**去看日志里的堆栈**

### 其他常见报告符号

| 符号/词 | 含义 | 怎么处理 |
|---|---|---|
| `F` (FAILED) | 断言失败 | 代码或测试有错 |
| `E` (ERROR) | 用例本身跑不起来（fixture 报错等） | 先修夹具/环境 |
| `s` (SKIPPED) | 主动跳过 | 看原因，别长期挂着 |
| `xfail` | 预期会失败 | 已知 bug，先记录 |
| `ERROR ... in fixture` | 准备阶段就炸了 | 通常是数据库/依赖问题 |
| `--cov` 里的 `Missing` | 哪几行没被测试执行到 | 见下一节 |

### 常用命令速查

```powershell
pytest                              # 跑全部（按 pytest.ini 的 testpaths）
pytest -v                           # 显示每个用例名
pytest tests/test_tasks_api.py      # 只跑一个文件
pytest -k create                    # 只跑名字含 create 的用例
pytest -m integration               # 只跑打了 integration 标记的
pytest -x                           # 第一个失败就停（调试时最常用）
pytest --lf                         # 只重跑上次失败的（last-failed）
pytest -v --tb=long                 # 失败时显示完整堆栈
pytest --cov=app --cov-report=term-missing   # 覆盖率 + 指出没覆盖的行
pytest --cov=app --cov-report=html  # 生成 htmlcov/index.html，浏览器里看哪行被标红
```

## 4. 覆盖率：读数、定位、以及"别被它骗了"

### 本项目实测覆盖率

```
Name                     Stmts   Miss  Cover   Missing
------------------------------------------------------
app\__init__.py              1      0   100%
app\config.py                7      0   100%
app\database.py             24      4    83%   47-51
app\dependencies.py         10      1    90%   28
app\errors.py               27      2    93%   78-79
app\main.py                 28      0   100%
app\models.py               16      0   100%
app\repository.py           39      0   100%
app\routes\__init__.py       0      0   100%
app\routes\tasks.py         26      0   100%
app\schemas.py              21      0   100%
app\service.py              44      4    91%   25, 73, 82-83
------------------------------------------------------
TOTAL                      243     11    95%
```

**怎么读这张表**：
- `Stmts` = 可执行语句数；`Miss` = 没被执行到的；`Cover` = 覆盖率
- `Missing` = **具体哪几行没被测到**（配合 `--cov-report=html` 可以在网页上看红行）
- **先看文件级的低分，再看具体行** —— 不是追求 100%

### 关键技能：判断"哪些没覆盖是可以接受的"

本项目那 11 行没覆盖，逐条分析给你看 —— **这就是"验收者思维"**：

| 位置 | 是什么代码 | 为什么没覆盖 | 该不该补测试 |
|---|---|---|---|
| `database.py:47-51` | `get_session()` 的函数体（开/关真实数据库连接） | 测试里用 `dependency_overrides` 把它换成了内存库，**这正是我们想要的效果** | 不用。它由"启动服务+手工点接口"覆盖 |
| `dependencies.py:28` | `get_db()` 的一行转发 | 同上，被夹具覆盖 | 不用 |
| `service.py:25` | 模块级 `_now()` 辅助函数（定义即执行，从未被调用） | 时间戳实际由 `models.py` 的 default 生成 | 可以删掉这行死代码，或不管 |
| `service.py:73` | PATCH 传了**空对象** `{}` 时的提前返回 | 没写这个用例 | **值得补**（边界值） |
| `service.py:82-83` | 更新时"新标题与别人重复"的检查 | 没写这个用例 | **值得补**（异常路径） |
| `errors.py:78-79` | 兜底 500 异常的处理器 | 只有代码真崩了才走 | 不用强测，属于防御性代码，已标 `no cover` 语义 |

**结论**：95% 里真正"该补而没补"的只有 2 处（`service.py:73` 和 `82-83`）。
**95% 覆盖率 + 这 2 处空白 = 一份可解释的测试现状**，比"100% 但全是废话断言"好得多。

> **记住这句话**：覆盖率衡量的是"哪些代码被执行过"，**不是"哪些行为被验证过"**。
> 一行 `assert True` 也能刷覆盖率，但它什么都没验证。
> 所以正确的用法是：**用覆盖率找"漏测的区域"，而不是用它当 KPI。**

### 动手：把那 2 处补齐（可选，10 分钟）

如果你想让覆盖率到 100% 并体验"写一个用例"的完整过程，可以让 AI 按这个模板写，**然后你自己审查**：

```

  2) 更新标题时与另一条任务的标题重复 → 应返回 409
每条用例都要写中文文档字符串说明它验证哪条规则。
```

## 5. 会读还不够：你要会设计用例（这是测试方向的核心能力）

### 5.1 三条最实用的用例设计方法

| 方法 | 一句话解释 | 例子（针对"新建任务"） |
|---|---|---|
| **等价类划分** | 把输入分成若干"类"，每类挑一个代表来测 | 合法标题 / 空标题 / 超长标题 |
| **边界值分析** | 错误最常发生在边界上，重点测边界及其两侧 | 标题长度 0 / 1 / 100 / 101 |
| **错误推测** | 凭经验猜哪里会坏（重复提交、缺字段、类型错） | 标题重复、priority 传字符串 |

### 5.2 每个功能都要覆盖的三类路径

```
正常路径 (Happy Path)    一切合规 → 期望成功
异常路径 (Error Path)    业务规则被违反、参数非法 → 期望明确的错误码
边界路径 (Boundary)      最小值、最大值、最小值-1、最大值+1、空值
```

**新手最常见的错误：只写正常路径。** 而真实系统里的 bug，80% 出现在异常和边界上。

### 5.3 练习：给"新建任务"列一份用例清单

先自己写，再对照下面 —— **写不出来就说明你还没真正掌握**：

| # | 类型 | 用例 | 输入 | 期望 |
|---|---|---|---|---|
| 1 | 正常 | 最小合法数据 | `{"title":"a"}` | 201，status 默认 pending，priority 默认 3 |
| 2 | 正常 | 全字段合法 | `{"title":"写论文","description":"...","priority":5,"status":"doing"}` | 201，字段原样返回 |
| 3 | 异常 | 缺必填字段 | `{}` | 422 |
| 4 | 异常 | 标题重复 | 两次相同 title | 第二次 409 |
| 5 | 异常 | 状态取值非法 | `{"title":"a","status":"finished"}` | 422 |
| 6 | 异常 | priority 越界 | `priority: 0` / `6` | 422 |
| 7 | 边界 | 标题长度 = 1 | `{"title":"a"}` | 201 |
| 8 | 边界 | 标题长度 = 100 | 100 个字符 | 201 |
| 9 | 边界 | 标题长度 = 101 | 101 个字符 | 422 |
| 10 | 边界 | 标题为空串 | `{"title":""}` | 422 |
| 11 | 异常 | 类型错误 | `{"title":123}` | 422（Pydantic 严格模式下的行为，可实测确认） |
| 12 | 异常 | 非法 JSON | body 写成 `not-json` | 422 |

**对照本项目实际用例**：`tests/test_tasks_api.py` 里 `test_invalid_payload_returns_422` 用 parametrize 覆盖了 3/5/6/10，
`test_create_then_read_task` 覆盖 1，`test_duplicate_title_returns_409` 覆盖 4。
**第 8、12 条本项目没测** —— 这就是一份真实的"测试缺口清单"。

### 5.4 接口测试的通用检查清单（贴墙版）

测任何一个接口，按这个清单过一遍：

- [ ] **正常**：合法输入 → 正确的状态码 + 正确的响应体
- [ ] **持久化**：写完之后**再读一次**，确认真的存进去了（不能只看返回 201）
- [ ] **必填**：缺每个必填字段各测一次 → 422
- [ ] **类型**：类型传错（字符串传数字）→ 422
- [ ] **边界**：长度/数值的最小、最大、最小-1、最大+1
- [ ] **枚举**：状态类字段传非法值 → 422
- [ ] **不存在**：查/改/删一个不存在的 id → 404
- [ ] **业务冲突**：违反业务规则（重复、状态不允许）→ 409
- [ ] **幂等**：同一个操作重复执行，结果一致
- [ ] **列表**：筛选参数生效、分页 `total` 与 `items` 语义正确
- [ ] **鉴权**（如果项目有）：不带 token → 401/403
- [ ] **错误格式**：错误响应的 JSON 结构是否统一可解析

## 6. 手工测试 vs 自动化测试（组会必问）

| | 手工测试 | 自动化测试 |
|---|---|---|
| 怎么做 | 打开 `/docs` 点按钮、填数据、看结果 | 跑 `pytest`，机器发请求、机器判断 |
| 优点 | 灵活、能发现"没想到的问题"、能看到界面 | 快、可重复、每次改代码都能跑、不会漏 |
| 缺点 | 慢、容易漏、依赖人的状态 | 只能验证"你写下来的期望"，写错一起错 |
| 什么时候用 | 探索新功能、UI 体验、一次性验证 | 回归测试、接口契约、核心规则 |

**正确姿势是搭配用**：
1. 新接口先用 `/docs` **手工点一遍**（探索）
2. 把确认过的重要行为**写成自动化用例**（固化）
3. 以后每次改代码跑 `pytest`（回归）

> 这个流程就是"测试左移 + 回归防护"的白话版，你写进周报完全够格。

## 7. 一个完整的"发现问题"全流程演练（面试/组会都能用）

**场景**：你发现"标记完成"接口有点怪。

| 步骤 | 做什么 | 具体动作 |
|---|---|---|

## 8. 让 AI 写测试，你当审查员（这是你未来的主力工作方式）

### 什么时候该让 AI 写测试
- ✅ 已有明确的被测函数和规则，需要批量生成用例
- ✅ 需要 parametrize 的边界值表格
- ✅ 需要把手工步骤翻译成自动化脚本
- ❌ 你自己都说不清"什么算对"的时候（先想清楚再让 AI 写）

### 审查 AI 写的测试，只问 4 个问题

| 问题 | 不合格的表现 |
|---|---|
| ① 这条断言失败时，说明**什么坏了**？ | 答不上来 → 废用例 |
| ② 它测的是**行为**还是**实现细节**？ | 断言了内部变量名/私有方法 → 脆弱，一重构就红 |
| ③ 它**真的会失败**吗？ | 删掉被测代码它依然通过 → 假测试（**务必试一次**） |
| ④ 它和已有用例重复吗？ | 同一个规则测三遍 → 冗余，维护成本翻倍 |

**第 ③ 条是绝招**：把被测的那行代码注释掉，跑一下，如果测试还是绿的，那这条测试就是摆设。
（本项目里 `repository.py` 的 `session.commit()` 就是绝佳的试验对象 —— 注释掉它，看哪些用例会红。）
